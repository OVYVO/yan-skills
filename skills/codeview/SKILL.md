# Codeview

## 代码审查目标

目标不是单纯挑错，而是用工程化视角给出可执行的改进建议，并帮助用户降低上线风险。

## 标准流程

### 1. 明确上下文与约束

若信息不足，优先向用户索取：

1. 审查范围：是否包含接口调用、状态管理、样式与无障碍
2. 技术栈：React、Vue、Nuxt、Next、Svelte，是否使用 TypeScript
3. 目标与风险：是否性能敏感、是否有可访问性或兼容性要求
4. 输入形式：是 diff、文件路径、通配符还是代码片段

若用户给出了文件路径或通配符，直接读取并集中审查。若没有给出文件路径，要求用户提供 diff 或关键文件。

### 2. 快速建模

先理解代码在做什么，再找问题。最少建模信息包括：

1. 入口：页面、路由或组件树的关键路径
2. 数据流：数据来源、修改位置和消费位置
3. 副作用：请求、定时器、事件监听、订阅以及清理逻辑
4. 关键用户路径：表单、分页、筛选、弹窗、登录态等

### 3. 检查清单

按严重性从高到低组织发现，并为每条问题提供“为什么重要”和“建议怎么改”。

#### A. 必须修

1. 功能正确性：逻辑错误、状态不一致、边界条件遗漏
2. 安全风险：XSS、敏感信息泄漏、不安全拼接
3. 无障碍致命问题：键盘不可达、焦点丢失、语义严重缺失
4. 性能灾难：渲染路径中的重计算、高频更新或死循环

#### B. 应当修

1. 可维护性：重复逻辑、过长函数、边界不清晰
2. 状态与数据流：派生状态混乱、来源不单一
3. 类型与健壮性：`any` 过多、断言滥用、空值路径遗漏
4. 错误处理：失败、超时、取消、重试和 UI 展示不明确
5. 渲染与组件：不必要重渲染、错误 key、低效事件绑定
6. 样式与布局：响应式断裂、可读性差、冲突风险高
7. 兼容性：关键 API 缺少降级策略

#### C. 可优化

1. 一致性：命名、风格、目录组织不统一
2. 可读性：魔法数、魔法字符串、重复常量
3. 文案与国际化：硬编码文案、格式化不统一
4. 测试与可验证性：关键场景覆盖不足

## 输出格式

输出时遵循下面结构：

```markdown
# 前端代码审查报告

## Executive summary

- 用 3 到 6 句话概括整体质量、主要风险和是否需要立即修复

## Key findings

- 每条发现统一包含：严重性 / 位置 / 问题 / 为什么重要 / 建议修改
- 按 Blocker -> Major -> Minor 分组

## Recommendations

- 给出最小修复集
- 如信息不足，列出 Need-to-know Questions
```

## 审查细节偏好

- 先给可验证的观察，再给建议方案
- 尽量贴近当前代码风格，避免无谓的大重构
- 遇到性能、无障碍和安全问题时，优先给出代码级修改建议

## 常见输入情况

1. 只有代码片段：只审查片段能覆盖的逻辑，并说明受上下文影响的假设
2. 提供 diff：优先审查变更相关的上下游路径
3. 只有需求描述：先列出待检查风险点，再索取关键文件
